JavaScript analysis reported javascript.xray.unsafe-regex

Expected behavior · high confidence

An automated scanner worried that some text-matching patterns might be slow enough to hang the browser. Looking at the actual code, the patterns have hard limits on how much they can repeat and were carefully designed so they cannot get stuck re-checking the same text over and over. The developer even notes that an earlier, slower pattern was found and removed. Nothing here shows a way for anyone to freeze the app, and at worst a slow match would only briefly slow down the user's own screen.

Technical evidence

Scanner reason: JavaScript analysis matched static JavaScript security signal javascript.xray.unsafe-regex. The match applies to this repository.

Contextual assessment: The scanner flags potentially unsafe regular expressions, but the visible patterns in the shipped frontend are deliberately written to avoid catastrophic backtracking. The main tag-stripping pattern bounds its repetition to a hard cap and uses mutually exclusive alternation branches, so no two branches can consume the same first character and there is nothing to backtrack between. The line-oriented custom-tag pattern is anchored and its execution loop is capped at a fixed iteration count. The refusal and error-matching patterns are short literal word lists with small bounded gap quantifiers, not nested unbounded quantifiers. The container-scanning routine was intentionally rewritten with index scanning instead of a backtracking pattern, with an in-code note that a pathological pattern was already encountered and removed once. No demonstrated super-linear matching on attacker-influenced reply text is shown by the supplied evidence. Even a worst-case slow match on model output would only affect the user's own tab, which is a local self-denial-of-service with low impact under the applicable threat model.

Impact: none · Exploitability: unlikely

Developer action: none

Contextual assessment: The flagged line is a curl-pipe-bash fallback for installing the bun runtime in a developer environment setup script. There is no obfuscation, no concealed second destination, and no execution triggered on end users of the extension. The behavior is the standard, well-known trade-off of piping a vendor installer to a shell, executed voluntarily by a developer setting up a build environment, which does not constitute demonstrated exposure of shipped or executable extension behavior to an attacker-controlled path.

Expected behavior · high confidence

The test script looks up two standard environment settings that say where a test browser is installed, so it can launch it for automated checks. Nothing is collected, copied, or sent anywhere, and this helper is not part of what users install.

Technical evidence

Scanner reason: JavaScript analysis matched static JavaScript security signal javascript.xray.serialize-environment. The match applies to this repository.

Contextual assessment: The environment-variable reads flagged by the serialize-environment heuristic occur in the test harness's browser-locator helper. It reads two specific variables that name a browser executable and a browser installation root, checks whether candidate locations exist, and passes the result to the browser launcher so the automated checks can run in environments where the test runner's default lookup fails. The read values are never serialized into a payload, written to storage, or transmitted to any destination; only path existence is checked.

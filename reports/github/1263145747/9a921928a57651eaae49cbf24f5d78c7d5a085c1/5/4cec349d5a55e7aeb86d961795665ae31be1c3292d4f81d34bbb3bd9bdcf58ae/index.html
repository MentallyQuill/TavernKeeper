Minor cautions

OpenGrep reported tavernkeeper.download-and-execute.shell-pipeline

Minor caution · high confidence

The project's developer-setup script can install a build tool by downloading and immediately running the tool maker's official install script. That practice is common but inherently trusting: whatever the server sends gets run. It only affects people setting up the project's source code for development, not the people using the finished extension, and the download comes from the tool's official website. No evidence shows anything malicious or tampered.

Technical evidence

Scanner reason: OpenGrep matched static-analysis rule tavernkeeper.download-and-execute.shell-pipeline. The match applies to this repository.

Contextual assessment: A developer setup script installs the bun runtime, falling back to piping the vendor's official installer script into a shell. This is a real supply-chain weakness class: executing a remote script means whatever the host serves runs with the developer's privileges, with no checksum or signature gate. However, the URL is the runtime vendor's documented official install location over HTTPS, the script only runs when a developer manually sets up a source checkout, it is not part of the shipped extension that Lumiverse users load, and no attacker-controlled content source or tampering path is demonstrated by the supplied evidence. Concretely harming a developer would require compromising the vendor host or the transport, which is not shown.

Impact: low · Exploitability: unlikely

Developer action: Consider downloading the installer to a file, verifying it against a published checksum or signature, then running it, so the setup does not blindly execute whatever a remote host returns.

The author visibly took care to keep them efficient, including caps on how much they can repeat. Nothing here suggests a real problem.

Technical evidence

Scanner reason: JavaScript analysis matched static JavaScript security signal javascript.xray.unsafe-regex. The match applies to this repository.

Contextual assessment: The scanner flagged unsafe regular expressions, but the supplied source shows the flagged patterns are bounded text-analysis regexes used for the extension's stated purpose: detecting cut-off replies, accidental refusals, and retry-after values in provider error text. The tag-matching patterns use mutually exclusive branches with capped repetition counts, the custom-block scanner limits iterations, and the comments document deliberate avoidance of backtracking blowups (including replacing a balanced-pair pattern with an index-based scan). No pattern in the evidence exhibits nested unbounded quantifiers or demonstrated catastrophic backtracking. The worst theoretical case for any flawed pattern here would be a slow match on adversarial reply text, a recoverable in-tab slowdown, which is not demonstrated by the supplied evidence.

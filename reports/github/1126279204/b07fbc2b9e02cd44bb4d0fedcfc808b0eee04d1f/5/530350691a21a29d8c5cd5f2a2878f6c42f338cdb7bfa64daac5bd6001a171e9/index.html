zizmor reported unsound-ternary

Minor caution · high confidence

A conditional expression used to decide the release description is written in a way that always picks the fallback text, so the intended keep-existing-notes behavior on re-runs does not happen. This can overwrite a typed description with a generic placeholder, which is annoying but harmless and public-facing.

Technical evidence

Scanner reason: zizmor matched workflow-security rule unsound-ternary. The match applies to this repository.

Contextual assessment: The release body parameter uses a pseudo-ternary whose intended empty-string result is falsy, so the fallback text is always selected, including on re-runs where the intent was to leave the body unset so existing draft notes are preserved. This is a logic defect in workflow expression handling, not a security control: the affected value is release-note text visible to the public, no secrets or untrusted input are involved, and the release remains a draft until a guarded publish step. The concrete effect is that draft notes typed into a re-run pre-release can be overwritten with the placeholder text.

Impact: low · Exploitability: unlikely

Developer action: Replace the empty-string pseudo-ternary with an explicit conditional, for example an if/else at job level or a step that sets the body only when the release is not already a draft, so an empty body is actually preserved.

Gitleaks reported generic-api-key

Minor caution · high confidence

The flagged string is a search-access token for a public character-browsing website. That site publishes the same token to every visitor of its own pages, and this app uses it only to search that site's catalog. It is not the user's password or API key, and it does not go anywhere unexpected. At worst, if the site changes the token, the app's search feature stops working until updated.

Technical evidence

Scanner reason: Gitleaks matched secret-detection rule generic-api-key. The match applies to this repository.

Contextual assessment: The matched 64-hex-character value is a fallback search token for the JannyAI character-discovery provider. The code's primary path fetches the token live by scraping JannyAI's own public, client-side JavaScript config, which by design ships this token to every browser visitor of that site. The hardcoded value is a cached copy of that same public token, used only as a Bearer header against the third-party search endpoint when the live scrape fails. It is not a user credential, not a project secret, and is not sent anywhere except the third-party service it belongs to. This matches the stated purpose of a character-discovery provider. The weakness is maintainability and fragility: the token is not a user secret but will silently break search if the third party rotates it, and its presence invites scanner noise. There is no demonstrated exposure of user data, credentials, or an attacker-controlled path to concrete harm.

Impact: low · Exploitability: unlikely

Developer action: Document in code that this token is a public client-side value belonging to the third-party site, not a secret, and consider a gitleaks allowlist entry to suppress future flags. Optionally handle token rotation gracefully rather than relying on a hardcoded fallback.

Gitleaks reported generic-api-key

Minor caution · high confidence

The code contains a long access code for another website's public search feature. That website already hands the same code to every visitor's browser, so it is not a private password of the app, its developers, or its users. It is only used to search that site, which is what the feature is for. The main downside is that the built-in copy can go stale and the search could stop working.

Technical evidence

Scanner reason: Gitleaks matched secret-detection rule generic-api-key. The match applies to this repository.

Contextual assessment: The matched value is a 64-hex-character bearer token hardcoded as a fallback in a production discovery-provider module. The data flow shows the provider first tries to scrape the same token live from the third-party character-site's public client-side JavaScript bundle (which is served to every visitor of that site), and only falls back to the embedded copy. This is a search-index access token belonging to the external site, not a credential belonging to the project, its users, or any user-configured provider key; it is sent only to that site's own search endpoint, which matches the stated discovery feature. No project or user secret is exposed and no exfiltration path exists. The weakness is maintainability and hygiene: a hardcoded third-party token can silently expire, and scraping a token out of another site's page markup is fragile. It does not demonstrate a concrete attacker-controlled path to meaningful harm for users.

Impact: low · Exploitability: unlikely

Developer action: Consider documenting that this is a third-party site's publicly distributed search token rather than a project secret, and marking the fallback for the secrets scanner so future audits are not misled. Prefer relying on the live token fetch where possible.

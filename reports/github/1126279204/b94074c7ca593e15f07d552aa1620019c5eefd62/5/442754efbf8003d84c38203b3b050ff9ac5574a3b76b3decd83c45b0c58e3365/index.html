zizmor reported secrets-inherit

Minor caution · high confidence

When a stable release is built, the Android job receives every stored secret rather than just the Android signing ones. Only maintainers can push release tags or start the run, so this is over-sharing within a trusted pipeline.

Technical evidence

Scanner reason: zizmor matched workflow-security rule secrets-inherit. The match applies to this repository.

Contextual assessment: The stable-release pipeline forwards every repository secret to the reusable Android build workflow in the same repository. The Android signing secrets match the signing and upload steps that publish builds, but blanket inheritance also exposes unrelated secrets to that job. The workflow starts only from a stable-version tag push or manual dispatch, both of which require write access, so no attacker-controlled trigger or untrusted data flow is demonstrated.

Impact: low · Exploitability: unlikely

Developer action: Pass only the Android signing secrets explicitly to the called workflow.

zizmor reported unsound-ternary

Minor caution · high confidence

A clever one-line shortcut meant to leave release notes alone on a re-run does not actually work: the default note text always wins, so any notes a maintainer typed into the draft can be replaced. It is an annoying bug in the release script, not a security hole.

Technical evidence

Scanner reason: zizmor matched workflow-security rule unsound-ternary. The match applies to this repository.

Contextual assessment: The release-body input uses logical operators to emulate a conditional. Because the intended empty-string branch is falsy in the workflow expression language, the fallback text is selected in every case, including re-runs where an existing draft already contains hand-edited notes. The documented intent of preserving typed notes on re-run therefore fails, and those notes can be overwritten. This is a self-inflicted automation correctness defect with recoverable loss of typed text; there is no attacker-controlled path, secret exposure, or user-facing harm demonstrated.

Impact: low · Exploitability: plausible

Developer action: Compute the release body in a preceding script step that emits an empty value on re-run, or gate the input with a genuine conditional, and verify the re-run scenario with a test.

Gitleaks reported generic-api-key

Minor caution · high confidence

The flagged string is a search key for a public character-directory website, the same key that website hands to every visitor's browser. It is not the app's own password and cannot reach anything belonging to the user; it just looks like a leaked secret to scanning tools.

Technical evidence

Scanner reason: Gitleaks matched secret-detection rule generic-api-key. The match applies to this repository.

Contextual assessment: The flagged constant is a fallback bearer token for a third-party character-search API used by the discovery feature. The surrounding code shows the primary path fetches this same token by scraping the provider's public client-side configuration script, which the provider serves to every browser visitor, so the constant is a public client identifier rather than a private project credential. It authorizes only search queries against that third-party service, is unrelated to this application's users, their stories, or their model-provider keys, and no concrete harm to users is demonstrated. The residual issues are hygiene: a secret-shaped literal in source that trips scanners, potential reliance on a token the provider can rotate, and downstream host allow-listing that appropriately constrains fetched content.

Impact: low · Exploitability: unlikely

Developer action: Document the value as a public client token with a scanner allowlist annotation, and prefer shipping only the dynamic token-fetch path so provider rotation degrades gracefully instead of depending on a stale constant.

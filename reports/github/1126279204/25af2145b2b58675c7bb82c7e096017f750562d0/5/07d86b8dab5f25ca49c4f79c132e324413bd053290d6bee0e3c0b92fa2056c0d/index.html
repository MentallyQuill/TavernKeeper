zizmor reported secrets-inherit

Minor caution · high confidence

The iOS preview build gets every stored secret even though it doesn't need any signing secrets. Only maintainers can trigger it and the script is the project's own, so this is a tidiness issue, not an open door.

Technical evidence

Scanner reason: zizmor matched workflow-security rule secrets-inherit. The match applies to this repository.

Contextual assessment: The pre-release iOS build job is invoked as a reusable workflow with blanket secret inheritance. The workflow fires on pre-release tag pushes and manual dispatch, which require existing write access; the called workflow is a same-repository file that, as reviewed, uses no Apple signing secrets at all and only the repository token. Passing all repository secrets where the called workflow needs essentially none is a least-privilege hygiene weakness. No attacker-controlled trigger or secret-exfiltration data flow is demonstrated in the supplied evidence.

Impact: low · Exploitability: unlikely

Developer action: Pass only the minimal secrets the iOS build workflow actually needs instead of inheriting all repository secrets.

zizmor reported unsound-ternary

Minor caution · high confidence

The release workflow tries to say 'if this is a re-run, keep the notes I typed; otherwise use the default text.' Because of how the condition is written, the default text wins in both cases, so a maintainer's hand-written release notes could get replaced. It is a small bug in the release recipe, not a security issue.

Technical evidence

Scanner reason: zizmor matched workflow-security rule unsound-ternary. The match applies to this repository.

Contextual assessment: The flagged expression uses a logical-operator construct that does not behave as a true ternary in the workflow expression language: when the intended 'empty' branch evaluates, its falsy value causes the fallback branch to be selected anyway. Per the adjacent in-file comment, the intent is to leave the release notes unset on re-runs so manually typed notes are preserved, so the construct defeats that intent and can overwrite a maintainer's draft notes. This is a correctness defect in maintainer-only release automation; no untrusted input, secret, or cross-boundary effect is involved.

Impact: low · Exploitability: unlikely

Developer action: Replace the pseudo-ternary with an explicit conditional (for example, setting the release-notes input only when the release state is not a draft re-run) so draft notes are genuinely preserved.

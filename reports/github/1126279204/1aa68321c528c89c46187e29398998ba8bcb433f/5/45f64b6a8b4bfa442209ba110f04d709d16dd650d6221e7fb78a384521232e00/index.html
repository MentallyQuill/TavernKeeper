zizmor reported secrets-inherit

Minor caution · high confidence

The release pipeline hands every secret the project stores to its Android build job. Since that job's definition lives in the same project and is written by the same maintainers, this is normal practice and not evidence of anything harmful. It is just broader than strictly necessary, so a future problem in that build job could touch more secrets than it needs.

Technical evidence

Scanner reason: zizmor matched workflow-security rule secrets-inherit. The match applies to this repository.

Contextual assessment: The release workflow's android build job passes all repository secrets to a reusable workflow via unconditional secrets inheritance. The called workflow is defined in the same repository under maintainer control, so this is a common CI pattern rather than an external exposure. The hygiene concern is that every repository secret, rather than only the ones the build needs, becomes available to the called workflow, which widens the blast radius if the called workflow or any action it uses is later compromised or changed. No attacker-controlled trigger, exfiltration path, or malicious consumer is demonstrated by the supplied evidence.

Impact: low · Exploitability: unlikely

Developer action: Prefer passing only the specific secrets each reusable build workflow needs, for example the GitHub token and any signing credentials, instead of inheriting all secrets.

zizmor reported unsound-ternary

Minor caution · high confidence

A conditional expression in the release automation is written in a way that always picks the same outcome, so re-running a pre-release build may stomp on notes a maintainer typed into the draft. It is a small logic bug in the project's own tooling, not something an outsider can exploit or that affects the app users get.

Technical evidence

Scanner reason: zizmor matched workflow-security rule unsound-ternary. The match applies to this repository.

Contextual assessment: The release-body input uses an and/or chain intended as a conditional, but in GitHub's expression language an empty string is falsy, so both branches resolve to the fallback text and the intended empty-on-re-run case never occurs. The observable effect is that the fixed pre-release banner is applied even when re-running against an existing draft, which can overwrite manually typed release notes. This is a correctness flaw in trusted automation logic: the inputs come from an internal guard step, no attacker-controlled data reaches it, and no secrets, exfiltration, or shipped-product behavior are involved.

Impact: none · Exploitability: unlikely

Developer action: Replace the and/or pseudo-ternary with a proper conditional expression so the release body is genuinely left unset when re-running an existing draft.

Gitleaks reported generic-api-key

Minor caution · high confidence

A scanner flagged an API key hardcoded in the app. Looking at how it is used, it is a publicly available search key from another website—the same key that site gives to every web browser—and it is only used to search that site for characters to download. It is not the project's own secret and not the user's key, so nothing sensitive is exposed. Hardcoding it is still untidy: it can stop working without warning and looks like a real secret to scanners.

Technical evidence

Scanner reason: Gitleaks matched secret-detection rule generic-api-key. The match applies to this repository.

Contextual assessment: A 64-hex-character bearer token is hardcoded as a fallback in a discovery provider for a third-party character-card site. The surrounding code shows the token is normally scraped at runtime from that site's own public client-side JavaScript, meaning it is a token the site already publishes to every browser visitor, not a private project or user credential. The token is sent only to that site's search endpoint to power a character discovery feature that matches the project's stated purpose; no user data, provider API keys, or story content is involved. The hardcoded fallback is a hygiene weakness because it embeds a third party's token and will silently rot or could be confused with a genuine secret, but the evidence does not demonstrate exposure of any sensitive credential.

Impact: low · Exploitability: unlikely

Developer action: Document inline that this is the third-party site's public client token, and consider dropping the hardcoded fallback in favor of failing gracefully and re-fetching the token, so it cannot be mistaken for a genuine secret.

zizmor reported unsound-ternary

Minor caution · high confidence

The expression chosen to leave the release notes blank on a re-run never actually produces a blank value, so the placeholder text is always used and could overwrite notes someone typed into a draft release. This is a release-pipeline bug, not a security issue, and it only affects maintainers publishing releases.

Technical evidence

Scanner reason: zizmor matched workflow-security rule unsound-ternary. The match applies to this repository.

Contextual assessment: The release-body parameter uses a chained and/or pseudo-ternary. In GitHub expression semantics, the intended-empty branch evaluates to an empty string, which is falsy, so the or-branch is taken in every case. The result is that the body always receives the fallback text, including on re-runs of an existing draft, where the surrounding comment says the notes should be left untouched. This is a demonstrated logic defect in the workflow, but it affects only release-note content in a maintainer-operated pipeline; there is no attacker-controlled input, secret exposure, or code-execution consequence, and the fallback text itself is a harmless static string.

Impact: low · Exploitability: unlikely

Developer action: Replace the chained and/or expression with a proper conditional, such as an if-based step or a format/if expression that yields an empty body when the release state is draft, so typed draft notes are preserved on re-runs.

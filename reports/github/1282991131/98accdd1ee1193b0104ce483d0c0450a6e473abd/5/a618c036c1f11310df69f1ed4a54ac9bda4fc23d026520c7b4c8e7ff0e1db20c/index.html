Related contextual observations

Session cookies never marked Secure, even when the app is served over HTTPS

low risk · high confidence

Login cookies are never marked as HTTPS-only, even when the app is set up with a secure web address. That is a deliberate choice so the app works on home networks without encryption, but it means the login cookie could be intercepted if someone uses the app over an insecure connection on a shared network. For the typical self-hosted home use case the practical risk is small.

Technical assessment

The advanced.useSecureCookies option is hard-coded to false rather than conditioned on the scheme of the configured base URL. The accompanying comment explains this is deliberate to keep cookie login working on plain-HTTP LAN deployments, but it also means that when an operator sets an https APP_URL, session cookies are still issued without the Secure attribute, allowing them to be sent over plain HTTP and potentially captured by an attacker positioned on the same network as the user. This is a conditional, network-adjacent weakness in a self-hosted, typically single-user app, not a demonstrated exposure in the supplied evidence.

Impact: low · Exploitability: plausible

Developer action: Consider deriving the Secure cookie flag from the configured APP_URL scheme (enable Secure cookies when the base URL uses https), so secure deployments get browser-enforced cookie protection while plain-HTTP LAN setups keep working.

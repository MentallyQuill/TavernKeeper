Contextual expected matches (2)

Gitleaks reported generic-api-key

Expected behavior · high confidence

The flagged text is the plugin's own sign-in app credential for Google's login service. Because this plugin runs entirely on the user's machine, that credential is designed to be included in the code every user downloads, and it is only ever sent to Google's official login service. The actual value was hidden from this review, so we cannot confirm it still works, but nothing in the supplied code shows it being used anywhere improper or exposing anything about users.

Technical evidence

Scanner reason: Gitleaks matched secret-detection rule generic-api-key. The match applies to this repository.

Contextual assessment: The scanner matched an OAuth client secret constant stored alongside a public OAuth client identifier. The surrounding code implements the authorization code grant with PKCE and a localhost loopback redirect, which is Google's native/public application model; in that model the client secret is not treated as confidential by the provider and must ship inside the distributed client bundle, so its presence in this repository is equivalent to its presence in every installed copy. Tracing actual use, the constant is sent only to Google's first-party OAuth token endpoint during code exchange and token refresh, together with the authorization code or refresh token. There is no third-party destination and no runtime retrieval of the secret from elsewhere. The matched value was redacted from the supplied evidence, so its current validity cannot be confirmed, and no concrete harm to plugin users is demonstrated. Google account tokens issued to users are obtained interactively from Google and are not derivable from this constant.

Impact: none · Exploitability: unlikely

Developer action: none

Credential access and network transmission in one file

Expected behavior · high confidence

The scanner noticed the plugin reading a saved login token and making an internet request in the same file. Here the token is your Google sign-in token saved by the plugin itself, and the request goes only to Google's own services to look up your account details and keep the token fresh. That is exactly what this plugin says it does, and the supplied code shows the token never travels anywhere except Google.

Technical evidence

Scanner reason: A credential source and an outbound network operation were detected in the same file.

Contextual assessment: The heuristic flagged a stored credential source and an outbound network request in the same file. Tracing the actual data flow, the credential is the plugin's locally stored Google OAuth access token, retrieved through the host application's argument API. The request attaches that token as a bearer header to Google's first-party user information endpoint to fetch the signed-in profile, and the same file's other requests send the authorization code, refresh token, and app credentials only to Google's own OAuth token endpoint. Every egress destination in the file is a Google first-party service, which matches the provider's stated purpose of authenticating users to a Google-backed model service. No third-party, proxy, or undocumented destination receives the token, and persistence is limited to the host application's own storage via its plugin API.

Impact: none · Exploitability: unlikely

Related contextual observations

OAuth paste-back login does not verify the state parameter

low risk · high confidence

When you sign in, the plugin creates a one-time marker and includes it in the Google web address, and it is supposed to check that marker when you paste the final address back. It skips that check. Someone would have to trick you into pasting a sign-in link from their account, and the worst result is the plugin using their account instead of yours, so the practical risk is small.

Technical assessment

The login routine generates a random state value when building the Google authorization URL, but the paste-back path extracts only the authorization code from the user-supplied redirect URL and never compares the returned state against the generated one. Omitting this check enables a login-fixation pattern in which a persuaded user pastes a redirect URL originating from an attacker-initiated session, causing the plugin to authenticate against the attacker's Google account instead of the user's. The interaction requires actively tricking the user into pasting an attacker-supplied URL, the token still comes from Google's legitimate endpoint, and the outcome is limited to which account the plugin uses, so concrete harm remains low.

Impact: low · Exploitability: unlikely

Developer action: Parse the pasted redirect URL, extract the returned state value, compare it against the state generated for this login attempt, and reject the exchange on any mismatch before using the authorization code.

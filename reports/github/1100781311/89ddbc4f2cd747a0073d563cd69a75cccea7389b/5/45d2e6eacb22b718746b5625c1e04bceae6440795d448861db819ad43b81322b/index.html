Minor cautions

Gitleaks reported generic-api-key

Minor caution · high confidence

The plugin contains a login key that is built into the copy every user downloads. This is normal for desktop-style Google sign-in apps, where that key is not treated as truly private. It is only ever sent to Google's own login servers, and nothing in the evidence shows it being used to steal anything from users. It is a minor housekeeping issue for the developer, not a danger.

Technical evidence

Scanner reason: Gitleaks matched secret-detection rule generic-api-key. The match applies to this repository.

Contextual assessment: A secret-scanner pattern matched a hardcoded OAuth client secret constant in the authentication module of a browser-distributed plugin. The surrounding code implements an OAuth authorization-code flow with PKCE against Google endpoints, and this constant is sent only to Google's own token endpoint during code exchange and token refresh. For an installed/public client type this constant is shipped to every user by design and Google does not treat it as confidential, so its presence in the repository is a hygiene weakness rather than a demonstrated user-facing exposure. All observed network destinations in this file are first-party Google OAuth endpoints; there is no exfiltration to any third-party host. The supplied evidence does not show any attacker-controlled path in which this constant produces concrete harm to end users.

Impact: low · Exploitability: unlikely

Developer action: Register the OAuth client as an installed/desktop application type, document that the client constant is public by design, and avoid treating it as a confidential secret. If the client type supports it, move to a flow that does not require a client secret. Do not reuse this constant for any server-side or confidential client.

Contextual expected matches (1)

Credential access and network transmission in one file

Expected behavior · high confidence

The plugin reads the sign-in token it saved earlier and shows it to Google's own servers to fetch your account name and picture. That is exactly how sign-in tokens are meant to be used, and the token only ever goes to Google, not to anyone else. This is normal behavior for a Google login feature, not a threat.

Technical evidence

Scanner reason: A credential source and an outbound network operation were detected in the same file.

Contextual assessment: The flagged pattern is a stored Google OAuth access token read via the host plugin API and sent as an Authorization header to Google's own userinfo endpoint to display the logged-in user's profile. This is the standard, intended use of an access token: it is transmitted only to the first-party Google API that issued it, over HTTPS, for a feature (login status and profile display) that matches the project's stated purpose of providing Google Antigravity authentication. The same file's other token-related network calls (code exchange and refresh) likewise target only Google's OAuth token endpoint. There is no transmission to any third-party or attacker-controlled destination, no obfuscation, and no use of the token beyond the documented authentication purpose.

Impact: none · Exploitability: unlikely

Developer action: none

Related contextual observations

Copy-paste redirect handling for OAuth callback

low risk · medium confidence

After signing in with Google, the user is asked to copy and paste the address of the page they land on back into the plugin. That is a clunky but common approach. The plugin does not double-check that the pasted link matches the login session it started, which is a small sloppiness, but nothing shown turns that into an actual attack on users.

Technical assessment

The login flow opens a Google authorization window, then asks the user to paste the redirected callback URL back into a plugin prompt so the authorization code can be extracted with a regex. This is a common workaround for plugins that cannot register a loopback listener, but it adds a manual step where a user could theoretically be social-engineered into pasting a crafted URL from elsewhere. The code does not validate the state parameter from the pasted URL and does not verify that the code originated from the flow this instance initiated. Any resulting token still goes only to Google's token endpoint in exchange, and tokens are stored via the host plugin API, so no concrete exfiltration or attacker-controlled harm is demonstrated by the supplied evidence.

Impact: low · Exploitability: unlikely

Developer action: Validate the state parameter from the pasted callback URL against the generated state before exchanging the code, and clearly instruct users to paste only the URL shown immediately after the Google sign-in screen.

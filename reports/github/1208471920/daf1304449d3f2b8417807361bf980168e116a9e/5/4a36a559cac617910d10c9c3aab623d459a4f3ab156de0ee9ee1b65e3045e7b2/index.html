Credential access and network transmission in one file

Expected behavior · high confidence

The scanner noticed that a login token and an internet request appear in the same file, which can sometimes signal theft. Reading the actual code, the token is only attached to calls the game makes to its own server to load or send your saved adventure chat, like showing your ticket at the venue that issued it. Nothing is sent anywhere else, so this is normal, expected behavior rather than a problem.

Technical evidence

Scanner reason: A credential source and an outbound network operation were detected in the same file.

Contextual assessment: The scanner flagged co-location of a credential source and a network sink, but the actual data flow is benign. The composable reads the application's own session token from its auth store and attaches it as a bearer authorization header on fetch calls to a fixed relative, same-origin API base path used for loading and posting adventure chat state. Every observed request stays within the application's own backend, which is the standard authenticated single-page-application pattern for a project of this stated purpose (a browser game with a backend GM service). There is no third-party or external destination, no dynamic or attacker-influenced URL, no obfuscation, and no transmission of any model-provider or unrelated credential. The scan result is a keyword-level capability heuristic, not demonstrated exfiltration.

Impact: none · Exploitability: unlikely
